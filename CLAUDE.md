# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Assets View — a self-hosted "Netflix for local files." Astro 6 SSR app (`@astrojs/node` standalone adapter) that browses images, videos, PDFs, and plain-text files (`.txt`, `.md`, `.json`, `.log`, `.csv`, `.yaml`/`.yml`) straight from the filesystem. **The filesystem is the source of truth** — there is no database, no auth, and no upload flow. State lives in a single in-memory index that a `chokidar` watcher keeps in sync.

## Commands

```bash
pnpm run dev        # Astro dev server with hot reload (http://localhost:2000)
pnpm run build      # Production build -> dist/
pnpm run start      # Run the built server (HOST=0.0.0.0 node ./dist/server/entry.mjs)
pnpm test           # Vitest unit + integration tests (single run)
pnpm run test:watch # Vitest watch mode
pnpm run test:e2e   # Playwright E2E — needs a server already running at :2000 (locally)
pnpm run typecheck  # tsc --noEmit (strict)
```

Run a single unit test: `pnpm exec vitest run tests/unit/scanner.test.ts` (or `-t "name"` to filter by test name).
Run a single E2E spec: `pnpm exec playwright test tests/e2e/home.spec.ts`.

Native binaries must be on `PATH` or video/PDF features silently degrade: `ffmpeg` + `ffprobe` (video thumbnails/metadata) and `pdftoppm` + `pdfinfo` from poppler-utils (`brew install poppler` on macOS). The Docker image installs these via apk.

## Architecture

**The in-memory index ([src/lib/scanner.ts](src/lib/scanner.ts)) is the spine of the app.** Everything else reads from it:

- `index` is a module-level singleton. `buildIndex()` walks `MEDIA_DIR` (up to `MAX_CATEGORY_DEPTH`), builds a `MediaItem` per file and a `Category` tree, and queues thumbnail generation as a side effect.
- A single `ready` promise runs `buildIndex()` once at module load, then installs the chokidar watcher. **Every page and API route must `await ready`** before reading the index — this is the standard entry guard, don't skip it.
- The watcher rebuilds the *entire* index on any `add`/`unlink`/`addDir`/`unlinkDir`. There is no incremental update — keep that in mind before adding expensive per-file work to the scan path.
- Read the index only through the exported accessors: `getMediaIndex`, `getItemById`, `getCategoryBySlug`, `getRecentItems`. Items are always sorted newest-first by mtime.

**ID / path scheme.** A `MediaItem.id` is the path relative to `MEDIA_DIR`, with each segment `encodeURIComponent`-ed and joined by `/` (`makeId` / `idToRelativePath`). IDs flow into URLs (`/api/media/<id>`, `/api/thumbnail/<id>`) and back. When serving files, every route re-derives the absolute path and validates it with the `safePath` pattern (resolve, then confirm it stays within the configured base dir) — this is the path-traversal guard. Never serve a filesystem path that hasn't passed `safePath`.

**Native module handling is deliberate and load-bearing.** `sharp`, `chokidar`, and `exifr` are externalized in [astro.config.mjs](astro.config.mjs) (`rollupOptions.external` + `optimizeDeps.exclude`) AND imported dynamically (`(await import('sharp')).default`) inside [src/lib/thumbnails.ts](src/lib/thumbnails.ts) and [src/lib/metadata.ts](src/lib/metadata.ts). This keeps Vite from trying to bundle native `.node` binaries at build time. If you add a native dependency, follow the same pattern (external + dynamic import) or the build breaks.

**Thumbnails ([src/lib/thumbnails.ts](src/lib/thumbnails.ts)).** Generated by `sharp` (images), `ffmpeg` at 10% duration (video), and `pdftoppm` then `sharp` (PDF, first page); text files have no generated preview and always fall back to the placeholder. Output is `400×225` JPEG cached under `CACHE_DIR/thumbnails/<xx>/<sha1(id)>.jpg`, sharded into 256 subfolders by the digest's first two hex chars (digest filenames — never derive cache paths from raw ids, sanitized names collide; and never point `CACHE_DIR` inside `MEDIA_DIR` without going through `isCacheDirPath` — see below). Cache validity is an **mtime check** (`thumbnailExists`): a thumb is stale if older than its source. A custom concurrency-limited queue (`queueThumbnail` / `drainQueue`, bounded by `THUMBNAIL_CONCURRENCY`) runs generation in the background; on-demand requests go through `requestThumbnail`, which shares the same queue (never call `generateThumbnail` directly from a route — that unbounds process spawning); missing thumbs fall back to `/placeholder-thumb.svg`.

**`CACHE_DIR` may be nested inside `MEDIA_DIR`.** `isCacheDirPath()` in [src/lib/paths.ts](src/lib/paths.ts) is the single guard against the scanner indexing its own generated thumbnails as media (which would then generate thumbnails-of-thumbnails, growing unbounded). It's wired into the recursive scan, the root-level scan, and the `chokidar` watcher's `ignored` option in [src/lib/scanner.ts](src/lib/scanner.ts) — all three must stay in sync if this logic changes.

**Search is split.** The server builds a lightweight `SearchIndexEntry[]` ([src/lib/search.ts](src/lib/search.ts)) and ships it to the client (via the page or `/api/search-index`). `filterIndex` then runs entirely **client-side** in the browser — there is no server search endpoint that takes a query.

**Routing.** Astro file-based routes under [src/pages/](src/pages/). Pages (`.astro`) render the UI; API routes (`.ts`) under `pages/api/` serve bytes — `media/[...slug].ts` streams files with validated HTTP range support (required for video seeking) and serves **only indexed items** (`getItemById`) — this is a security boundary: it keeps non-media files and symlinks under `MEDIA_DIR` unreachable, don’t relax it to raw path serving. `thumbnail/[...slug].ts` serves/generates thumbs, `search-index.ts` returns the JSON index. Viewers live in [src/components/viewers/](src/components/viewers/) and carry their own client-side keyboard/zoom logic; PDF.js is bundled from `pdfjs-dist` and served from our own origin (worker via Vite `?url`), not loaded from a CDN.

**Dev-mode routing quirk ([astro.config.mjs](astro.config.mjs)).** In Astro 6 dev mode, any URL ending in a file extension (e.g. `/media/photo.jpg`) is intercepted as a static-asset request *before* the Vite plugin/middleware stack runs, so `[...slug].astro` never sees it — `enforce: 'pre'` plugins are too late. The workaround is a raw `prependListener('request', ...)` on the dev server's HTTP server that strips the extension from `/media/*` URLs and stashes the original slug in an `x-media-slug` header for the page route to read. This only runs via `configureServer` (dev-only); production builds are unaffected. Don't "simplify" this into a normal Vite plugin hook — that's the bug it works around.

## Config & environment

Behavior is driven by env vars (see [.env.example](.env.example) / README): `MEDIA_DIR`, `CACHE_DIR`, `SITE_TITLE`, `PORT`, `MAX_CATEGORY_DEPTH` (scan depth, default 6), `THUMBNAIL_CONCURRENCY`. In Docker Compose, `media/` is mounted read-only and `cache/` read-write. TypeScript path alias `@/*` -> `./src/*`.

**⚠️  Important: The `dev` script must use `dotenv` to load `.env` at process start.** Environment variables are read at module load time (before Astro loads `.env`), so the scanner module must have access to `process.env.MEDIA_DIR`. The dev script is configured as `"dev": "dotenv -- astro dev"`. If this prefix is removed, `MEDIA_DIR` will default to `./media`, the scanner will find no files, and opening any image will return 404. This has been a recurring issue; a warning is logged if `MEDIA_DIR` is still the default value.

**Styling is Tailwind 4** wired in as a Vite plugin (`@tailwindcss/vite` in [astro.config.mjs](astro.config.mjs)) — there is no `tailwind.config.mjs` and no `@astrojs/tailwind` integration. The theme (the `netflix-*` colors, font) lives in the `@theme` block of [src/styles/global.css](src/styles/global.css); add design tokens there as `--color-*` / `--font-*` variables, not in a JS config.

## Troubleshooting

**"No media found" / 404 on image open:**
- Check the server logs for `[scanner] ⚠️  MEDIA_DIR is using default ./media`
- This means env vars didn't load at startup (recurring issue, fixed 3+ times)
- Verify package.json `dev` script is: `"dev": "dotenv -- astro dev"` (not just `"astro dev"`)
- The `dotenv` prefix is required because the scanner module reads `process.env.MEDIA_DIR` at module load time, before Astro loads `.env`

## Tests

Unit + integration tests live in [tests/](tests/) and run under Vitest (`globals: false` — import `describe`/`it`/`expect` from `vitest`). Integration tests read real sample files from [tests/fixtures/media/](tests/fixtures/media/); add fixtures there when testing scan/metadata/thumbnail behavior against actual files. E2E specs use Playwright (chromium only); locally they expect a server already running, while CI starts one via `pnpm run start`.

## CI & Docker

`.github/workflows/docker-publish.yml`: on every push/PR to `main`, a `test` job installs `ffmpeg` + `poppler-utils`, then runs `pnpm run typecheck` and `pnpm test`. On push to `main` or a `v*` tag (not on PRs), a `build-and-push` job builds a multi-arch (amd64/arm64) image via Buildx/QEMU and pushes to GHCR (`ghcr.io/<repo>`), tagged by branch, semver, sha, and `latest` on the default branch.

The [Dockerfile](Dockerfile) is a two-stage Alpine build: the build stage installs `python3 make g++ vips-dev` (sharp may compile from source if no prebuilt binary matches), the runtime stage installs only `ffmpeg poppler-utils vips` and runs as the non-root `node` user. The healthcheck has a 120s `start-period` because the root route blocks on the initial `buildIndex()` scan, which can take minutes for a large library. [docker-compose.yml](docker-compose.yml) mounts `./media` read-only and a named `cache` volume read-write — note the app has **no authentication**, so the compose file's port comment warns against exposing it beyond a trusted network without a reverse proxy in front.
